# October 2026 eMudhra TLS response

The requirements lock pinned certifi 2025.1.31. Update it to 2026.10.19 for the OpenAI/HTTPX clients used by the DML agents.

The incident concerns compromised intermediate signing keys, not a leaked private key belonging to this repository. No known incident certificate was found in the repository scan; an old trust bundle can still accept certificates issued through the compromised intermediates.

This guide covers this project's environments and known package tools; it does not establish that an entire machine or other users' environments are remediated. In that scope, upstream pip must be >=26.2.2 and uv, if installed, must be >=0.13.4; distribution backports require the vendor verification described below. If pixi or sigstore is installed, the PSF advisory also requires pixi >=0.82.1 and sigstore >=4.5.1. Inventory those clients through their owning package manager or configured installation directory, update through a trusted, integrity-verified channel or retire them, and verify each absolute executable with --version before using it. Updating certifi or uv does not replace pip's private CA bundle. Remove or retire unused older installers so they cannot be invoked later.

The upstream pip bootstrap below requires Python >=3.10. For an older interpreter, obtain a verified distribution fix as described below or stop using its pip for network installs and retire that environment. To recreate it, install a maintained Python through a trusted, integrity-verified distribution channel, bootstrap pip in the new environment, then reinstall and test this project. Legacy environments are not remediated without that verification or replacement. For Python >=3.10, run the PSF's hash-verified bootstrap with each environment's own Python:

On [externally managed/system Python (PEP 668)](https://packaging.python.org/en/latest/specifications/externally-managed-environments/), do not apply the pip bootstrap to the system interpreter or use --break-system-packages. Apply the distribution vendor's patched pip/certifi/CA packages through its package manager. Verify the vendor security advisory or packaged CA evidence: a backported fix may retain an older upstream version number. If no verified vendor fix exists, retire that interpreter from network package operations and recreate the project environment using a trusted maintained Python. A new virtualenv does not remediate an old system pip left in use.

```sh
python -m pip install --upgrade --no-deps "https://files.pythonhosted.org/packages/3f/06/3e4420302363fbb71be3c7f35ce042f54bfca330e3e66b3a2e3c4cca579f/pip-26.2.2-py3-none-any.whl#sha256=fd7f4dfa8190e014013b9f08f3e973f4e4c26ffd179a204895533a7254813a70"
```

After bootstrapping pip, check `python -m pip --version` in every environment. If uv was installed by that Python's pip, update that copy with `python -m pip install --upgrade "uv>=0.13.4"`. This does not update standalone, pipx, Homebrew or Cargo installations: update each through its owning installation method using a trusted channel and verified artifact integrity, or retire it. Do not bootstrap a replacement through an unpatched installer's unverified network download.

After securing the installer, explicitly reinstall the application dependencies in every affected project environment; changing a requirements file alone does not update an existing installation. In a user-managed pip environment that uses certifi, run `python -m pip install --upgrade "certifi>=2026.10.19"`, then reinstall this project's requirements and verify they did not downgrade it. For a uv-managed project with a patched lockfile, use the patched uv to run `uv sync --locked`; use the resulting environment's Python for verification. Where certifi is used, check `python -c "import certifi; print(certifi.__version__, certifi.where())"` and require >=2026.10.19 before restarting the application. Distribution-managed environments follow the vendor-backed remediation above. Applications without certifi still require verification of their actual TLS trust source.

Inventory active and inactive installations using each environment/package manager's inventory and configured directories: known project virtualenvs (including inactive .venv folders), pipx/uv tool environments, pyenv interpreters, and standalone/Homebrew/Cargo locations. PATH enumeration (`type -a uv` in Bash/Zsh, or `where.exe uv` in Windows Command Prompt/PowerShell) is only a supplemental check and misses inactive environments. For every discovered environment, check its own Python's pip; for every uv copy, check its absolute executable path with `--version`, then patch or retire it. Installing a second pip-managed copy does not prove another active or inactive copy was upgraded. Follow [uv's installation-method guidance](https://docs.astral.sh/uv/getting-started/installation/#upgrading-uv). Recheck newly created Python environments because ensurepip may seed an older pip.

Recreate or update environments, rebuild images, restart processes, and verify the installed bundle before treating a running deployment as remediated. This PR does not deploy anything. Inspect OS trust and any SSL_CERT_FILE, SSL_CERT_DIR, REQUESTS_CA_BUNDLE, or custom TLS context independently; repository changes cannot prove deployed settings. Unused or future clients that choose their own CA bundles need their own verification.

Sources: [certifi 2026.10.19](https://github.com/certifi/python-certifi/releases/tag/2026.10.19), [Python Security Response Team guidance](https://discuss.python.org/t/information-for-python-users-regarding-emudhra-emsign-ca-certificate-security-incident/109576).
